# mission_arc_check — 规划约束的地面校验

读任务文件与参数文件，离线判断整条航线里每个协调转弯**可不可飞**、不可行的**差在哪**、
**改成什么才可行**。零 Flash 代价，能在派工前跑。

分支 `dev-planning`（工作目录仍叫 `UAV-work/p06`，路径与分支名不一致是历史原因，
改目录要重建 worktree，代价大于收益）。

## 为什么需要它

判定的数学早就写好了——`AC_ArcNav::plan_feasible()` 检查倾角预算与偏航速率——
但它**唯一的调用点在飞行中**（`ArduCopter/mode_auto.cpp:1885`），在前一段航段正在
规划时才算这个弯可不可飞，判定失败则**静默回退**到普通盘旋圈，没有任何 GCS 提示。
飞手看到的是「这个弯飞得比预期慢、形状也不对」，看不到「这个弯本来就不该这么规划」。

本工具把同一套判定挪到地面、按整条任务遍历，并补上飞控里做不到的两项检查。

## 用法

```bash
python3 Tools/mission_arc_check/mission_arc_check.py \
    任务.waypoints  参数.param [更多参数文件...] \
    --yaw-rate-max 57 --yaw-rate-source "真机偏航阶跃辨识 2026-09-xx，20° 倾角下"
```

参数文件可给多份，**后者覆盖前者**。SITL 一次运行的生效参数是分层叠加的
（`copter.parm` 默认 + 机型 `parm` + 场景 `--set` 覆盖），只读其中一层会按错误的
参数值判定，而报告看起来完全正常。

退出码：`0` 全部可行；`1` 有转弯不可行；`2` 输入有误。可直接挂进派工流程当门禁。

### `--yaw-rate-max` 与 `--yaw-rate-source` 为什么是必填

飞行中的判定取 `ATC_SLEW_YAW`（经 `get_slew_yaw_max_rads()`，实为
`min(ATC_RATE_Y_MAX, ATC_SLEW_YAW)`）。**那是允许值，不是能力值。** 参数设得高于
机体真实能力时，判定会放行一个飞不出来的弯。地面工具若也从参数推这个数，就只是
把同一个错误搬到地面。所以它必须由人显式给出，并说明出处——报告会把这句话原样
印上去，让读报告的人自己判断可信度。

口径：要的是**作业倾角下**的可达偏航速率，不是悬停时的。倾角上去后偏航权限会被
滚转俯仰挤占，悬停值是上界不是作业值（SITL 实测悬停 78.4 °/s，20° 倾角下 54.7–59.1）。

无真机数据时可用 `--yaw-from-sitl-model` 贯通流程，报告会标注它含占位量。

## 三项判定，以及每项判的是什么

| | 判什么 | 数据来源 |
| :-- | :-- | :-- |
| 倾角预算 | `v²/r ≤ g·tan(倾角上限 × 70%)` | `PSC_ANGLE_MAX`，为 0 则回退 `ANGLE_MAX` |
| 偏航速率 | `v/r ≤ ψ̇_实测 × 50%` | **命令行必填**，不从参数推 |
| 前段 lead-in | 入弧点前的航段 ≥ `plan_feasible()` 输出的 `lead_in_m` | 任务几何 |

第三项在飞控里**不存在**。`plan_feasible()` 成功时输出 `lead_in_m`，含义是「前一段
航段应当瞄过入弧点这么远、且不得在这段距离上减速」，但没有任何地方检查前一段本身
是否长于它——它拿到的是一个转弯，不是整条任务，无从检查。作业段短、行距大时这个
承诺物理上兑现不了：函数返回 `true`，飞机却飞不出计划的弧。

**不判**围栏、地形、电量、喷洒，以及普通航点转弯的 SCurve 掉速。

## 三个容易搞错的口径

**半径会被截断成整数米。** `AP_Mission.cpp:1124` 是 `uint8_t radius_m = abs_radius`，
C 的浮点转整数是截断不是舍入。任务里写 2.5 m，机上按 **2 m** 执行——更紧的弯、
偏航需求高 25%。本工具复现了这个量化并在报告里标出，否则校验的是飞机不会用的半径。

**过渡长度用 `PSC_JERK_XY`，不是 `WPNAV_JERK`。** `get_shaping_jerk_NE_msss()` 直接
返回前者，全仓库没有任何地方调 `set_shaping_jerk_NE_msss()`。参数文件里有
`WPNAV_JERK` 而无 `PSC_JERK_XY` 时工具会警告——那种配置下改 `WPNAV_JERK` 不影响转弯。

**SITL 的 54.7–59.1 °/s 不是不确定区间，是两个 `ATC_RAT_YAW_FF` 取值各自的实测值**
（FF=0 → 54.7，FF=0.30 → 59.1）。偏航前馈直接产生力矩、不必等误差攒起来，所以它
改变的是能力而不只是跟踪质量。取中值 57 会在两头各错约 4%——而验收那条航线的余量
只有 3.1%，本工具第一次跑验收时就因此把一条实飞掉速 0.19% 的航线判成了不可行。
`--yaw-from-sitl-model` 现在按参数文件里的 `ATC_RAT_YAW_FF` 选，不取中值。

## 跳行建议为什么要连台阶位置一起报

跳行数是 `ceil(R_req / (行距/2))`，**`ceil` 把连续量压成了台阶**。后果是参数改动
常常一行也省不掉：偏航上限 50 → 59.1 °/s 提高 18%，在 3/4/5 m/s 三档作业速度上
跳行数一行未变。而「离台阶边缘 0.1 m」和「离 2 m」是完全不同的处境——前者一次微调
就翻档。所以只报 `R_min` 现场不知道该干什么，报告同时给出当前在第几行、至少要第
几行、距下一档还有多少米，以及**降到多少速度能少跳一行**（真正能省行的是降速）。

判可行的转弯也报余量。可行不等于稳妥，余量 3% 和 60% 是完全不同的处境。

## 判据独立性：两层，都不由本工具自己界定

一个只会自我一致的校验工具，比没有工具更坏——它会给出「已经检查过」的错觉。

### 单元层：由 C++ 界定

`tests/test_crosscheck.py` **现场构建并运行**
`libraries/AC_WPNav/tests/test_arcnav_feasibility --dump-table`，把 C++ 在 14,580 行
网格上的输出与本包 `arcnav.py` 的逐点比对。

- **表是现场生成的，不读仓库里的文件。** 一份提交进仓库的表，在 C++ 改了而没人重新
  生成时对拍照样通过——比对的是陈旧快照。那和「工具自证」是同一种错觉，只是更隐蔽，
  因为它看起来有外部基准。构建不了时**明确跳过并把原因打出来**，不退回读旧表。
- `arcnav.py` 用 `struct` 做 float32 仿真，与飞控逐步同精度。双精度算出来的边界与
  飞控的边界差一点点，而「差一点点」就是可飞与不可飞的分界。
- **验过它真能失败**：把 `SMOOTHSTEP_PEAK` 从 1.5 改成 1.4999（0.007%），对拍报出
  27,461 处不一致。一个从不失败的对拍等于没有对拍。

```bash
python3 Tools/mission_arc_check/tests/test_crosscheck.py   # 需要 ./waf configure --board sitl
python3 Tools/mission_arc_check/tests/test_check.py        # 纯 Python，无需构建
./build/sitl/tests/test_arcnav_feasibility                 # C++ 侧 9 条
```

### 系统层：由实飞轨迹界定

**校验说可行的航线，必须在 SITL 里真的飞得出来——判据是实飞轨迹，不是校验工具
自己的输出。**

`reproduce.py` 的 `upload_mission()` 会把上传的任务落盘成 `mission.waypoints`
（写进本次运行目录，与 `model.json` / `algo.parm` / `logs` 并排）。校验吃的是
**飞机实际上传的那份**，不是照同样入参再生成一条——再生成的那条与实际上传的差一个
字段，校验就是在校验另一条航线，而且这种偏差不会有任何提示。

2026-09-04 实测（`ATC_RAT_YAW_FF=0.30`，`WPNAV_SPEED=300`）：

| 场景 | 工具判定 | 实飞 |
| :-- | :-- | :-- |
| `--swath 12`，R=6 m | **可行**（余量 3.1%，偏航最紧） | `ARCN` 有记录；弧内最低速 **2.99 m/s**、掉速 **0.19%**、航向误差 4.51° |
| `--swath 5`，R=2.5→2 m | **不可行**（倾角与偏航同时超标） | `ARCN` **无任何记录**——`set_arc()` 拒绝、AUTO 静默回退；进弧前速度掉到 **0.03 m/s**、弧内最低 0.15 m/s |

**反例那一行同时是两件事的证据**，第二件比第一件重要：

1. 工具判不可行是对的；
2. **静默回退确实发生了。** `arc_*` 指标全部来自 `ARCN` 日志，一条记录都没有意味着
   `set_arc()` 拒绝了这个弯、AUTO 落回普通盘旋圈。飞机几乎停在地头（进弧前 0.03 m/s，
   相对 3 m/s 的作业速度掉 99%），而 GCS 上**一条消息都没有**。

第二件就是空洞 B——「判定失败不上报，回退无声，事后不可追溯」。在此之前它只能引
`mode_auto.cpp` 里那句代码注释（`// Not flyable - fall through to the ordinary
handling`）来说明，现在有了实测。这条线立项的理由就在这一行里。

复现：

```bash
python3 Tools/eft_issue_repro/reproduce.py uturn-auto --variant p06-accept \
    --swath 12 --set WPNAV_SPEED=300 --set ATC_SLEW_YAW=12000 \
    --set ATC_RAT_YAW_P=0.60 --set ATC_RAT_YAW_I=0.12 --set ATC_RAT_YAW_FF=0.30
# 把 --swath 12 换成 5 得到反例

d=Tools/eft_issue_repro/runs/<本次目录>
python3 Tools/mission_arc_check/mission_arc_check.py $d/mission.waypoints \
    Tools/autotest/default_params/copter.parm $d/params.parm $d/algo.parm \
    --yaw-from-sitl-model
```

跑 SITL 前先 `pgrep -af "[a]rducopter|[r]egression.py"`——TCP 5760 全机唯一。

### 这两个点证明了什么，没证明什么

证明的是**判据在这两点上不误报**：一条能飞的没被判死，一条飞不了的没被放行。

没证明的是**判据的松紧对不对**。正例的余量只有 3.1%，而 SITL 在 P06 掉头场景上
并非逐次可复现：同一份代码、同一台机器连跑两轮，`uturn-arcnav` 的弧内掉速变动
**4.65%**（主线那边独立测得，n=2）——**比余量还大**。余量 3.1% 的样本落在边界
内侧，可能只是这一次的运气；它说明不了边界画在了正确的位置。

（多数指标其实是逐比特可复现的：主线那轮刻画里 39 个数值指标有 30 个极差为零，
波动集中在少数几个场景上，`uturn-arcnav` 的掉速是其中最大的一个。所以这里说的不是
「SITL 有噪声」这种笼统说法，而是**这一个指标恰好在波动的那一组里**。）

要检验边界本身，需要一组余量分布开的航线（+30%、+10%、+3%、−3%、−30%）各飞
一次，看实飞的翻转点是不是落在判据的零余量处。那才是判据校准，本工具目前**没有
做**。

**暂不做的理由，以及解除条件。** 判据的绝对松紧由 `AC_ARCNAV_YAW_RATE_FRACTION
= 0.5` 与 `AC_ARCNAV_TILT_FRACTION = 0.7` 两个编译期常数、连同给进来的偏航能力值
共同决定。现在这两样一个只有源码里一句「留一半余量给入弧暂态」支撑，另一个是 SITL
模型推的。此时做扫描会得到「翻转点在零余量附近」——**那是必然的，判据就是这么定义
的，等于什么都没测出来**，只测到了判据自洽。

真机偏航辨识回来之后这组扫描才有意义：那时能力值是实测的，扫描测的就变成「预算
取一半合不合理」，那是个真问题。**这就是解除条件。**

**记在这里而不是略去，是因为略去之后这份 README 读起来会像判据已经验过。**
