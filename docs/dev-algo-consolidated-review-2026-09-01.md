## 1. 结论先行

当前分支已经形成一套有价值的“问题复现—算法原型—SITL 回归—日志量化”闭环，尤其是单电机停转降级、固定磁偏角辨识、姿态模式围栏和协调圆弧。但它还不是可直接宣称七项问题全部解决的生产版本。

本轮最重要的结论如下：

1. `EFT_CAAC` 与 SITL 都能完成编译；`54663c19ff` 时记录的 `EFT_CAAC` 固件只剩 **7,196 B Flash**，已经进入必须管理的工程风险区；后续提交仍需重新记录最终 Flash。
2. `54663c19ff` 阶段的集中回归原始结果为 13/15；另外两项由并发 SITL 抢占固定端口造成，并非算法失败。独立复测后，两项算法判据均通过。后续套件已继续扩展，不能把这轮 15 项当作当前完整验收集。
3. P01 的正常 LAND 场景以约 0.43 m/s 触地、约 1.80 s 后上锁，但这不是新机载算法的
   改善结果；分支只完成复现与排因，末段拉平、识别提速和触地后平滑卸载均未交付。
4. P02 的 VFF 候选在同一 5 m/s 急反向场景中显著减轻 I 项负担，但峰值俯仰速率没有下降，不能仅凭 SITL 数字宣称“抽动已消失”。
5. P04 只证明“有 ESC RPM 的单电机停转、目标构型、指定参数和风场”可控；桨叶断裂/脱桨可能表现为电机超速与强振动，当前低转速检测器明确不覆盖。
6. P05 的手动姿态模式和 LOITER 已有预防性围栏原型与 SITL 证据，现场六次越界也促成了
   制动律重写；但修正后尚未实机复飞。AUTO 用例只验证越界后的 Brake 距离，不能算预防性不越界。
7. P06 的 AUTO/GUIDED 协调圆弧在已测工况有效，但仍绕开动态避障、地形跟随和飞行中围栏变化，生命周期契约也未完全收口。
8. P07 的现场问题是 LOITER 手动画圈，不是自动 CIRCLE；已有证据支持它与 P02 共用速度
   相关力矩/I 项跟踪根因，同时还受倾角权限限制。自动 CIRCLE 的参考生成缺口应归 P06，
   不能用它替代 P07 验收。
9. 现阶段不建议把整个飞控改成 INDI/增量式控制。应先补齐实机模型、日志、分配器残差反馈和轨迹前馈；若以后引入 INDI，放在可切换的自定义控制器边界内做 A/B。

## 3. ArduPilot 在本项目中的实际执行链路

目标构型的控制主链如下：

```text
传感器后端/驱动
  -> INS/AHRS/EKF3 状态估计
  -> Copter flight mode（AUTO/LOITER/ALT_HOLD/...）
  -> AC_WPNav / AC_Loiter / AC_ArcNav
  -> AC_PosControl（位置->速度->加速度/推力向量）
  -> AC_AttitudeControl（推力向量/航向->角速度目标）
  -> 角速度 PID + VFF
  -> AP_MotorsMatrix（六旋翼混控/失效重分配）
  -> PWM/ESC/电机
```

调度表 `Copter::scheduler_tasks[]`（`ArduCopter/Copter.cpp:113`）开头的 `FAST_TASK` 序列以目标板 400 Hz 运行。当前循环先执行角速度控制和电机输出，再更新 AHRS、惯性状态和 flight mode 目标，因此存在刻意的一周期流水线：本周期低层使用上一周期模式目标，本周期模式计算供下一周期使用。新增算法必须尊重这个时序，不能把跨层状态当作“同一时刻原子更新”。

> 这段历史上是一个名为 `Copter::fast_loop()` 的函数，上游 `01766eee01`（2022-04-01）把它逐句改写成调度表开头的 `FAST_TASK` 条目，执行顺序原样保留。`FAST_TASK` 填的是 `rate_hz = 0`、`priority = FAST_TASK_PRI0`，`AP_Scheduler::run()` 对优先级 ≤ `MAX_FAST_TASK_PRIORITIES`(3) 的条目跳过限频与时间预算判断，每 tick 无条件按表序跑完，因此时序与旧实现一致。**本仓库已无 `fast_loop` 这个符号**，按该名字检索代码会扑空。

主要接入点：

| 能力 | 当前模块 | 关键接入 |
| --- | --- | --- |
| 着陆 | `ArduCopter/mode_land.cpp`、`land_detector.cpp` | U 轴位置控制、落地检测、spool state |
| 高速反拉 | `AC_AttitudeControl_Multi` | 角速度 PID 后的速度力矩前馈 |
| 磁对齐 | Compass、AHRS/EKF3、离线工具 | 自定义旋转参数、SITL 注入、日志辨识 |
| 动力失效 | `AP_MotorsMatrix` | RPM 检测、摘除、伪逆约束分配、yaw 降级 |
| 围栏 | `AC_Fence`、`AC_Avoid`、各 flight mode | 违规检测、预防限制、违规动作三条不同链路 |
| 平滑航线 | `AC_WPNav`、`AC_ArcNav`、AUTO/GUIDED | S 曲线、协调圆弧、航向/曲率约束 |
| 圆周抽动 | `AC_Circle`、`AC_PosControl` | 圆周参考生成、NE 位置/速度/加速度输入 |

## 4. 本轮实际改动

本轮没有实现新的大算法，只合并和补齐已由测试直接证明必要的最小改动：

### 4.1 N-02 气流力矩前馈飞行状态门控

涉及：

- `libraries/AC_AttitudeControl/AC_AttitudeControl.h`
- `libraries/AC_AttitudeControl/AC_AttitudeControl_Multi.cpp`

行为：

- `_landed_gain_ratio` 显式初始化为 0；
- 未解锁、spool state 非 `THROTTLE_UNLIMITED`、速度估计无效时，VFF 清零并复位滤波器；
- VFF 随 `landed_gain_reduction()` 的同一比例渐隐，避免 PID 已退让而 PID 后置前馈仍与地面反力对抗。

该改动只在 `ATC_VFF_RLL/PIT` 非零时产生效果；默认值为 0，默认飞行行为保持关闭。

### 4.2 reverse 场景入口修复

涉及：`Tools/eft_issue_repro/reproduce.py`

`run_reverse()` 原先读取未定义变量 `mode`，每次都在起飞后触发 `NameError`。现改为显式默认参数 `mode="LOITER"`，P02 专项得以真正运行。

### 4.3 固定 SITL 端口互斥

涉及：`Tools/eft_issue_repro/reproduce.py`

所有场景共用 TCP 5760 及辅助端口。本轮出现两个回归进程并发，后启动实例报 `Address already in use`，下一用例还可能误连到另一实例。新增非阻塞文件锁：检测到并发场景时立即给出占用进程号，不启动第二架 SITL，避免把基础设施冲突包装成算法失败。

这只是止住误连；集中报告仍应进一步区分 `INFRA_ERROR / INVALID_SCENARIO / FAIL / PASS`。

## 6. 七项问题的当前状态与建议

### P01 着陆末段与触地后对抗：部分关闭

已关闭：现有 SITL 的触地速度回归门限。

未关闭：触地后 1.80 s 才上锁；刚性地面模型不能复现起落架弹性、冲击峰值和触地后六路 PWM 极差。

建议：

1. 将验收拆成 `末段下降率、触地冲击、land_complete 延迟、撤推延迟、触地后电机不均衡` 五项；
2. 增加柔性起落架/地面接触模型，或接 Gazebo 接触模型；
3. 现场日志至少提供 `CTUN/PSC/ATT/RATE/MOTB/RCOUT/EV` 与同步视频；
4. 不要用“最终上锁时间”替代 land detector 各内部条件的逐项诊断。

### P02 高速运动反拉抽动：原型有效，未交付

建议：

1. 把 reverse 加入集中回归，并定义峰值角速度、角加速度/jerk、姿态误差、I 项换向时间；
2. 增加 `VFF input/output/fly_scale/active EKF lane/airspeed or groundspeed source` 日志；
3. 覆盖 3/5/7/10 m/s、空载/满载、前后/左右反拉、顺逆风和不同电量；
4. 参数由实机回归辨识，不直接采用本轮 0.0088；
5. 若 PID 后置前馈继续保留，应把合成后的执行器饱和反馈纳入抗积分饱和。

### P03 磁力计与 IMU 坐标对齐：辨识链路通过，自动补偿未交付

建议：

1. 只把稳定的固定安装偏角写入 `ROTATION_CUSTOM_* / CUST_ROT*`，不要飞行中无条件在线改坐标；
2. 在线估计必须有可观测性门槛、置信度、多罗盘一致性、EKF lane 一致性和回滚；
3. 增加 0° 负样本、±15/30/60/90°、不同倾角、磁干扰和双罗盘故障注入；
4. 先做“地面/标定航线自动建议值 + 人工确认”，再考虑空中闭环写参数。

### P04 电机或桨叶失效：单电机停转部分关闭

建议：

1. 分开检测“电机停转、部分失推、桨叶脱落/断裂、ESC 遥测丢失”；RPM 低只覆盖第一类；
2. 将约束分配器的 achieved wrench、各轴残差、夹紧电机、可用控制裕度反馈给 PID anti-windup 和 failsafe；
3. 对 1–6 号电机、0/2/4/6 m/s 风、不同航向、载荷/电量、不同失效高度做矩阵测试；
4. `MOT_FAIL_IDX` 必须有解锁/重启清理和显式告警，避免持久参数把下一架次带入降级混控；
5. 桨叶失效应融合 RPM、命令-RPM 残差、ESC 电流、IMU 振动和角加速度创新；
6. 目标是受控应急着陆和限制区域内落地，不承诺完整任务与航向保持。

### P05 电子围栏内稳定飞行：手动模式部分关闭

建议：

1. 测试和文档区分：目标合法性检查、飞行中预防限制、越界后 failsafe；
2. 将真实 22–26 m 田块、`FENCE_MARGIN=1 m`、凹多边形、顶点/边心、顺风和 GNSS 偏差纳入回归；
3. AUTO 若目标是绝不越界，不能只依赖越界后 Brake，任务路径与 OA 必须在生成阶段受围栏约束；
4. 失去位置估计时不能静默放行，应定义 BRAKE/LOITER/LAND/RTL 的可配置降级。

### P06 航线、航点、起飞到田间和避障平滑：核心圆弧部分关闭

建议：

1. 统一使用连续位置、速度、加速度，必要时 jerk/曲率连续的轨迹契约；
2. 起飞点到较低田面应联合规划水平和垂向 S 曲线，而不是“先升高—平飞—直降”的折线；
3. 障碍绕行轨迹必须回到同一平滑器，不让 Dijkstra/BendyRuler 的折线直接成为控制目标；
4. `AC_ArcNav` 需补模式退出、任务跳转、failsafe、拒绝后回退、动态围栏/障碍、terrain alt 的统一生命周期；
5. GUIDED 圆弧里“飞手保持 yaw 权限”的空分支应明确为真正的混合权限，或删除误导注释；
6. 以作业段速度误差、转弯半径、航向误差、加速度、jerk、喷幅重叠/漏喷为联合验收指标。

### P07 圆周飞行抽动：已定位主要结构缺口，未关闭

建议：

1. `AC_Circle` 输出与圆周几何一致的切向速度和向心加速度，不再只移动位置点；
2. 将 `ANGLE_MAX`、`PSC_ANGLE_MAX`、当前 thrust margin、yaw rate/accel 同时纳入可行速度；
3. 达不到目标速度时应明确限速并记录原因，不让参考点跑远后靠位置误差追赶；
4. circle 与 P06 共用轨迹/曲率能力接口，避免两套圆弧生成器逐渐分叉；

### 10.7 P02 高速反拉：代码如何一步步形成当前方案

#### 第一步：先把真实系统缺失的扰动放进仿真（`19b4e4c3c3`）

原始 ArduPilot 多旋翼 SITL 没有“平移来流引起机体滚转/俯仰力矩”这一项。若仍用默认
模型跑高速反拉，速率环根本看不到真机上随速度换向的配平负担，任何控制器都显得很好。
该提交因此先改仿真侧，而不是先改控制器：

```text
SIM_Frame::calculate_forces()
  vel_air_bf（机体系空速）
    -> roll torque  += gain.x * body-right speed
    -> pitch torque += gain.y * body-forward speed
    -> torque / moment_of_inertia
    -> rotational acceleration
    -> SITL 姿态运动
```

代码位置是 `libraries/SITL/SIM_Frame.cpp` 和 `SIM_Frame.h`。新增 JSON 字段默认全为 0，
所以其他 SITL 模型行为不变；`eft_hexa.json` 才显式启用
`velocity_torque_gain=[18,-18,0]`。同一提交还加入近地增升/溃散模型，为 P01 服务。

这里要区分“复现模型”和“实机模型”：50 kg、`[12.5,12.5,25] kg·m²` 惯量、2 m
轴距、4.71 m² 总盘面积和 18 N·m/(m/s) 系数都是首轮占位/反向校准值。它能让控制链
出现同量级现象，用来比较算法开关；不能凭它证明真实飞机的力矩规律就是严格线性或系数
就是 18。

#### 第二步：用速度前馈接替慢积分配平（`5ec348af80`）

真机日志显示 `PIDR.I/PIDP.I` 与机体系侧向/前向速度强相关。旧控制链只有速率 PID 的
I 项能长期抵消这类恒定扰动力矩；高速反向后外扰符号迅速改变，而旧 I 项仍保留原方向，
于是出现“先卡住、I 项慢慢换向、随后追上”的持续姿态误差。

该提交在 `AC_AttitudeControl_Multi::rate_controller_run_dt()` 中把补偿放在速率 PID
之后、六旋翼混控之前：

```text
AHRS velocity NED
  -> 可选减 EKF wind（得到近似空速）
  -> NED 转机体系（forward/right）
  -> 2 Hz 低通
  -> forward * ATC_VFF_PIT / right * ATC_VFF_RLL
  -> ATC_VFF_MAX 限幅
  -> rate PID output + SysID output + VFF
  -> AP_MotorsMatrix 六旋翼分配
```

四个新参数分别控制滚转增益、俯仰增益、输出上限和是否使用风估计。两个增益默认 0，
因此合入代码本身不会改变默认飞行。速度估计不可用时清零输出并复位滤波器，避免恢复后
把陈旧滤波状态突然注入电机。

#### 第三步：从日志拟合增益，而不是凭感觉调（`5ec348af80`、`0468935ed3`）

`fit_vel_ff.py` 将机体系速度作为自变量、对应轴 `PID*.I` 作为因变量做最小二乘，斜率
作为前馈增益候选。随后绕圈测试暴露出使用条件：持续圆周中速度方向不断旋转，I 项来不及
稳态收敛，得到的斜率会系统性偏小；因此拟合必须使用足够长的匀速直线段，并用另一架次
验证残余斜率是否下降。

现有两份后期 SITL 日志的重新计算结果为：

| 配置 | `PIDP.I` 对前向速度斜率 | 相关系数 | 含义 |
| --- | ---: | ---: | --- |
| VFF 关闭 | `+0.00810/(m/s)` | 0.867 | 速度相关配平主要由 I 项承担 |
| VFF 约 `+0.0088` | `+0.00189/(m/s)` | 0.881 | 剩余斜率约为原来的 23%，前馈已接走大部分稳态负担 |

这支持“前馈减轻 I 项换向负担”，但峰值俯仰速率仍约 118°/s，没有同步下降，所以不能
把它直接翻译成“肉眼抽动已完全消失”。

#### 第四步：补地面/起降门控（`d79de03cd6`、`957454cbfe`、`54663c19ff`）

首版 VFF 位于 PID 之后，不受 PID 的 `landed_gain_reduction()` 保护。只要地面上的
EKF 报出水平速度，首版就可能在未解锁、spool-up 或触地后继续给滚转/俯仰力矩。两个
并行修正最后在 `54663c19ff` 汇合：

1. 未解锁或 spool state 不是 `THROTTLE_UNLIMITED` 时硬清零并 reset 滤波器；
2. 即使 spool 门打开，也按 `1 - _landed_gain_ratio` 从 0 平滑淡入/触地淡出；
3. 将此前未显式初始化的 `_landed_gain_ratio` 初始化为 0；
4. 同时修复后来演进中 `run_reverse()` 误用未定义 `mode` 导致场景必崩的问题；
5. 为所有固定端口场景加进程锁，避免两个 SITL 互连产生伪结果。

要注意时间关系：`5ec348af80` 时的早期 `run_reverse()` 直接固定 LOITER，可以运行；
未定义 `mode` 是后续扩展脚本时引入的回归，不应倒推为“最早的 VFF A/B 从未运行”。

#### 第五步：把不可见补偿变成可测量量（`71502a0f3e`）

该提交新增 25 Hz `VFF` 日志，记录滤波前机体系速度、滤波后速度、限幅前力矩、最终
输出和落地缩放比例。于是可以直接回答：增益是否生效、是否被 `VFF_MAX` 截断、是否在
地面关闭、输出为何为零。只有增益非零时才写日志，默认配置不增加带宽。

#### 第六步：修正 EKF lane 与交叉验证口径（`99907a46c1`）

初版拟合固定读 core 0，但飞控姿态和速度来自当时的 primary lane；真机 lane 切换时，
两侧数据可能来自不同 EKF。新版本按 `XKF4/NKF4.PI` 选择 primary core，并剔除切换点
前后 2 s。若存在 `VFF` 日志则优先使用控制器实际采用的滤波速度，并剔除落地淡出样本。

#### 第七步：纳入回归，但只设“防退化护栏”（`581b25ddc8`、`21db563a9c`）

P02 专项最初游离在集中回归外，后来加入三项护栏：反向次数、峰值俯仰速率/误差、
`pitch_i_span`。首版门槛误用了“VFF 已开启”的候选结果去要求默认 VFF=0 配置，第一次
运行就误报；`21db563a9c` 改为基于默认配置自身的门槛。这段演进说明每个数值必须绑定
固件提交、参数集和物理模型，不能脱离 variant 名称复制。

#### 当前 P02 的实际解决程度

已经形成：可控的速度力矩扰动模型、默认关闭的补偿算法、离线辨识、飞行状态门控、内部
日志和防退化回归。尚未形成：教练机实测模型、不同风/载荷/速度的增益调度、与同步视频
对应的主观抽动验收，以及非零参数进入量产默认值。因此当前状态应称“候选算法链闭合，
实机交付未闭环”。

### 10.8 P07 圆周抽动：问题路径如何被逐步澄清

1. `147e5390e9` 首先用自动 `CIRCLE` 模式做 2 m 半径逐档测试。它发现
   `AC_Circle::calc_velocities()` 会依据半径和可用加速度主动限速，因此没有出现预期
   倾角饱和。这不是 P07 被证伪，而是说明测试走错了控制路径。
2. `0468935ed3` 随即增加 `loiter-circle`：在 LOITER 中让滚转/俯仰杆按正余弦旋转，
   直接产生旋转倾角目标。该路径确实能在高档贴住 15° 限幅；同一个 P02 VFF 又把姿态
   误差和 I 项摆幅明显降低，说明“旋转的速度相关配平需求追不上”与“倾角权限不足”是
   两个并存、可分离的问题。
3. `3c7695dc90` 修正自动 `AC_Circle::calc_velocities()` 的可行速度计算。圆周速度需满足
   `v²/r <= a_available`，原代码只看 `WPNAV_ACCEL`；新代码再取
   `g*tan(min(PSC_ANGLE_MAX, 动态 althold 倾角限幅))`，两者的较小值，并保留 50% 加速度
   余量。默认场景行为基本不变，因为当时已有其他限制；而且 `ANGLE_MAX` 仍在更后层生效、
   这里看不到，所以它只修了自动 CIRCLE 的一部分可行性口径，不解决手动画圈抽动。
4. `581b25ddc8` 加入集中回归时却选择了自动 `circle`，最初错误挂名 P07；
   `03b87206c7` 把它更正为 P06 自动 CIRCLE 护栏。提交说明称“手动场景尚未建立”并不
   准确：`loiter-circle` 自 `0468935ed3` 起一直存在；真正缺的是把它纳入集中回归并定义
   能代表肉眼抽动的角加速度/jerk与视频同步判据。

所以 P07 当前不是“没有复现工具”，而是“已有手动圆周专项场景，但自动回归覆盖和实机
视频闭环仍缺失”。它与 P02 共享姿态/速率控制改进，同时还需要单独处理倾角、推力和
可实现曲率的权限限制。

### 10.9 “IMU 失真/动力不一致”替代根因应如何理解（`5e5dd769eb`）

`check_powertrain_imu.py` 在 00000219/220/231 三份真机日志上得到的原始数字可以复现：
高/低机动 IMU 加速度分歧比约 0.84/0.77/1.01；六电机全程转速极差/均值约
41.7%—47.1%，电流约 106%—115%，RCOU 均值不对称约 8.1%—12.6%。

但实现与结论之间要留出边界：

1. 脚本说明写“相同油门下比较”，代码实际按整段飞行直接计算逐机均值，没有按相同
   PWM、姿态、速度和载荷配对；
2. 奇偶电机的 RCOU 均值本身长期相差约 100—176 PWM，这足以解释相当一部分 RPM/
   电流均值差，可能来自控制器抵消常态偏航力矩，不等于电机硬件性能一定不同；
3. 对 00000231 做近似同 PWM 分箱后，部分奇偶转速差仍存在，说明问题值得继续查，但还
   需排除正反桨气动差、ESC 转速/电流标定差和机架扭矩不平衡；
4. IMU 高机动分档未放大，只能说“这三架次按该指标未支持大机动 IMU 分歧”，不能排除
   高频混叠、安装点杆臂加速度、时间同步误差或短时削顶。

建议把下一步拆成两条独立证据链：电机台架/系留状态下建立每一路 `PWM→RPM→推力→电流`
曲线，再看同指令残差；IMU 则比较频谱、时延、温漂、clip 发生窗口，并补偿不同安装位置
的刚体角加速度。这样才能区分“控制器为了抵消机架气动不对称而主动给不同 PWM”和“同一
指令下某套电机/桨/ESC 确实性能异常”。

### 10.10 P06 匀速转弯：从“航点拼圆”到固件轨迹原语的完整演进

P06 在 `dev-algo` 中是一条很典型的迭代链：先证明问题不是靠继续增大控制参数就能解决，
再用飞控外部设定点证明正确参考轨迹可行，最后才把轨迹生成器接入固件。它当前解决的是
**定高、定速、已知圆心和半径的作业航线协调转弯**，不能扩大解释成 P06 的所有子场景均已
完成。

#### 第一步：证明普通航点转角存在几何性掉速（`98efc72d40`）

新增 `route` 场景后，直线上的密集航点可以保持 1.98—2.00 m/s；真正的问题出现在方向
切换。SCurve 将转角前后两段速度向量混合，转角中部的速度模长近似为：

```text
v_corner = v_work * cos(turn_angle / 2)
```

90°、45°、30° 三组结果分别为 1.44、1.85、1.93 m/s，与公式在 0—2% 内吻合。
`WPNAV_ACCEL` 从 150 提至 250 cm/s²、`WPNAV_JERK` 从 1 提至 3，90° 掉速仍约
28%→27%；连接段从 12 m 加到 40 m 也不改变最低速。这一步排除了“只要增大加速度/jerk
参数或拉长航段就能消除任意转角掉速”的假设。加速度上限仍能改善路径误差，但不能改变
速度向量合成的几何结果。

#### 第二步：证明航点拼接只有在大半径、长小段时勉强可用（`a3b7edc286`、`d46eb5c65e`）

`uturn` 场景比较 square、arc、spline 和 spline-arc。半圆切成 7 段后，每个转角约
25.7°，单次理论损失只有约 2.5%；但如果每段太短，SCurve 还没有建立便进入下一次混合，
误差会累积。2 m/s 时，R=2.5/8/12 m 的实测掉速分别约 75%/9%/2%。

换成植保作业的 5 m/s 后问题更明显：R=3/12/30 m 的掉速约 83%/53%/12%。也就是说，
若继续用航点逼近圆弧，可能要跳过约十条作业线、占用 30 m 半径，仍无法真正匀速。这使
“增加一个连续圆弧轨迹原语”从优化建议变成有量化依据的架构需求。

#### 第三步：先在飞控外验证三阶解析参考（`8ca83fe37f`）

`uturn-guided` 不改固件，而是在 50 Hz 下向 GUIDED 连续发送圆弧的三阶参考：

```text
位置 p(phi)       决定圆弧几何
切向速度 v(phi)   模长恒为作业速度
向心加速度 a(phi) = v^2 / R
```

同一物理模型下，2 m/s、R=3 m 的掉速从航点式 83% 降至解析圆弧约 1%；5 m/s、
R=10/14 m 时约为 5%/3%。R=7 m 需要约 20° 倾角，几乎用尽 GUIDED 的
`PSC_ANGLE_MAX`，因没有跟踪余量仍掉速 31%。因此入口必须在飞行前检查
`atan(v²/(R*g))`，而不能先接受不可实现轨迹、再让控制器在空中饱和。

#### 第四步：首版 `AC_ArcNav` 几何正确但控制契约错误（`a672d368ef`）

首版在 `libraries/AC_WPNav/AC_ArcNav.*` 中实现固定圆弧，并由 GUIDED 的
`MAV_CMD_NAV_LOITER_TURNS` 显式触发。调用链为：

```text
GCS_MAVLink_Copter::handle_command_int_nav_loiter_turns()
  -> ModeGuided::set_arc_destination()
  -> AC_ArcNav::set_arc()（倾角/入口速度检查）
  -> ModeGuided::arc_run()
  -> AC_ArcNav::update()
  -> AC_PosControl::set_pos_vel_accel_NEU_m()
  -> update_NE/U_controller()
  -> AC_AttitudeControl
```

这个版本每拍按 `omega*dt` 的墙上时钟推进目标角。结果是飞机沿着正确的圆飞，却掉速
55%—77%：目标点继续以理想速度向前跑，飞机稍一落后便形成更大的沿轨位置误差，位置
控制器饱和后反而更跟不上。该提交把自己明确标为 WIP，没有把“能编译、几何正确”包装成
算法已完成，这是正确的阶段结论。

#### 第五步：参考点改由实际跟踪能力推进（`ea7fa75741`）

参考推进改用与 `AC_WPNav::advance_wp_target_along_track()` 同类的 governor：

```text
track_error = 位置误差在目标行进方向上的投影
track_vel   = 实际速度在该方向上的投影
dt_scalar   = clamp(0.05 + (track_vel - kP*track_error)/target_speed, 0, 1)
path_progress += target_speed * dt * filtered(dt_scalar)
```

`dt_scalar` 再按横向加速度/jerk 对应的时间常数低通，避免参考推进率颤动。由此得到
2 m/s、R=3 m 掉速约 3%，5 m/s、R=12 m 掉速约 2%；R=3 m、5 m/s 等超过倾角预算的
组合在入口直接拒绝。该提交还新增 `ARCN` 的 `Prog/Gov/Spd/Tgt/PErr`，并把统计窗口从
估算时间改为 `Prog=0.05—0.95`，修正了此前把出弧悬停减速算入弧内的测量错误。

这里的关键不是“把目标速度调大”，而是修正了规划器与位置控制器之间的契约：参考轨迹
必须根据跟踪误差推进，不能脱离飞机的可实现状态独自按时钟运行。

#### 第六步：把机头方向和偏航能力纳入轨迹可行性（`97f84ab7fb`）

此前只给期望航向角，没有给切线旋转速率，机头会持续落后于路径切线。新版本调用
`input_thrust_vector_heading_rad(thrust, heading, heading_rate)`，其中
`heading_rate=v/R` 作为偏航前馈，并新增 `ARCN.HdgE`。

这又暴露出第二个硬约束：六旋翼偏航依靠各旋翼反扭矩差，能力通常弱于滚转/俯仰；即使
向心倾角可实现，`v/R` 也可能超过偏航速率。该阶段用最大偏航速率的 80% 作为预算，
超过即拒绝。之后代码将保留比例收紧为 50%，给扰动恢复留出更多余量。

#### 第七步：从曲率阶跃改成连续过渡（`9888f73d45`、`03e681085a`）

裸圆弧在入口把曲率从 0 直接跳到 `1/R`，因此横向加速度和偏航速率也同时阶跃。
`9888f73d45` 改为“入口过渡—定曲率圆弧—出口过渡”，先用线性曲率斜坡，并按
`L=v³/(R*jerk)` 计算过渡长度；航向是曲率对弧长的积分，位置以 512 个中点步预积分。
同时沿规划路径做航向前视，而不是用实测速度方向，避免侧风下机头追随地速方向而偏离
喷幅中心线。

`03e681085a` 又发现线性曲率虽然消除了偏航速率阶跃，却仍在两端产生偏航角加速度/力矩
阶跃，于是改成两端导数为零的 smoothstep 曲率。其峰值斜率是平均斜率的 1.5 倍，过渡
长度必须相应增加。航向前视也从固定值改成入弧渐增、出弧渐减，否则前视点会在第一拍
越过短过渡段，重新制造满偏航速率阶跃。

最终过渡长度同时满足三个下限：位置控制器 jerk、航向前视距离以及偏航角加速度能力。
其中前视变化会额外放大命令偏航角加速度，代码对这个二次约束取正根，而非忽略该项。
这使轨迹达到“位置、切向速度、向心加速度连续变化；曲率及其端点斜率连续”的程度，
比简单圆弧或折线更接近用户所说的“丝滑”。

#### 第八步：接入 AUTO，随后用着陆回归修复分支污染（`03e681085a`、`fc66f127be`）

AUTO 复用 `MAV_CMD_NAV_LOITER_TURNS`：圈数 `<=0.5` 解释为协调转向，更多圈数仍走原有
定点盘旋。接入不是只加一个 `SubMode::ARC`，还必须处理前后航段：

1. `set_next_wp()` 在前一作业直线末端提供弧入口切线前方 10 m 的虚拟 next point，使
   当前航点成为 fast waypoint；否则 `wp_nav` 会在入弧前先减速到零；
2. `arc_start()` 检查入口速度、倾角、偏航约束，临时把 PosControl 横向加速度和修正
   上限提高到所需向心加速度的 1.2 倍；
3. `arc_run()` 持续输出三阶参考和切向航向；
4. 弧完成后保持 ARC 子模式一拍，让 `verify_circle()` 识别生成器已结束并推进任务；
5. 交接时恢复 `WPNAV_*` 的速度/加速度限制，40 个循环仍无人接管则退回 LOITER。

入弧前最低速度由约 0.02 m/s 提高到 2.98 m/s。现存 AUTO 日志中，3 m/s、R=6 m
的有效弧段最低约 2.997—2.999 m/s，掉速约 0.03%—0.10%；平均航向误差约 4.51°、
峰值约 19.0°。

但是首次接入在 `switch` 中复用了原来由 LAND fallthrough 到 `LOITER_TURNS` 的结构，
错误地把 LAND 的 `p1` 当圈数、把落地点当圆心，导致“航点接 LAND”任务悬停不下降。
`fc66f127be` 增加 `next_cmd.id == MAV_CMD_NAV_LOITER_TURNS` 的显式判断后才恢复着陆。
这是 P06 修改影响 P01 的真实回归案例，也说明集中回归必须跨问题运行。

#### 后续补强：方向注释和围栏预检查（`2b1722c290`、`d77cb9757b`）

`2b1722c290` 只修正三处顺/逆时针注释，代码方向没有改变。`d77cb9757b` 发现
`AC_ArcNav` 直接写 `AC_PosControl`，不经过 `AC_Avoid` 或路径规划器，于是在 AUTO/GUIDED
接受圆弧前按每 5° 对理想圆采样并调用 `AC_Fence::check_destination_within_fence()`。

这个补丁是必要的，但提交自身已证明仍不充分：拒绝 ArcNav 后退回普通 circle，普通
circle 也可能越界；采样的是理想圆而非 smoothstep 过渡形成的实际曲线；没有运行期处理
风、定位漂移或飞行中围栏改变。几何上无法在栏内完成的任务应在任务上传/规划阶段拒绝，
而不是飞到弧入口才回退。

#### P06 当前证据边界与集中建议

已经有代码和 SITL 证据支持的范围：

- 固定高度、给定圆心/半径、入口速度已建立的 AUTO/GUIDED 协调转弯；
- 三阶位置/速度/加速度参考、沿轨 governor、倾角/偏航预检查和 ARCN 可观测性；
- 3 m/s、R=6 m AUTO 与 5 m/s、R=12 m GUIDED 两个代表工况保速。

仍未解决或尚未形成充分证据的范围：

1. 起飞后同时前飞和下降到较低田面的三维平滑过渡；当前 ArcNav 高度 `_alt_u_m` 固定，
   垂向速度和加速度均为 0；
2. 避障路径的连续曲率重建；ArcNav 不接收 OA 的折线，也不经过 `AC_Avoid`；
3. 任意航点角度、连续多个弯、terrain-following、强风、满载和 GNSS 偏差；
4. 动态围栏和运行期实际机体包络约束；
5. GUIDED `arc_run()` 中“保留飞手 yaw 权限”的 `if` 为空语句，实际始终执行自动切向
   航向，注释和控制权契约不一致；
6. 模式退出、任务跳转、failsafe 和异常拒绝后的统一 stop/恢复路径；
7. `LOITER_TURNS<=0.5` 被重新定义为定速转向会改变旧任务语义，且固定 10 m lead point
   未由速度、过渡长度或任务空间自适应计算。

建议保留 `AC_ArcNav` 作为可复用轨迹能力，但将入口语义、三维轨迹、OA/围栏、生命周期
和参数化边界逐步收口。当前最准确的状态是：**P06 的水平 U 转核心算法已由多轮失败和
修正形成闭环；P06 全问题尚未关闭。**

### 10.11 P03 磁力计与 IMU 坐标对齐：已经做到什么，尚未做到什么

这一阶段只有三个提交。它没有新增机载在线估计器，而是建立了“可注入的小角度安装误差、
专项航线、离线辨识、利用 ArduPilot 现有参数补偿、SITL 复飞确认”的工程链。提交标题中
的“闭环打通”应按这个含义理解，不能解释成飞机已经会在空中自动修改磁力计坐标系。

#### 第一步：让 SITL 能表示离散朝向之外的安装误差（`0d6b513474`）

原 SITL 支持 `SIM_MAG1_ORIENT` 这类离散旋转，却不能表达 GPS 杆安装面不平、支架公差
造成的几度或任意非整数角偏差。该提交新增 `SIM_MAGn_ANGL` 三轴角度，并在
`AP_Compass_SITL::_timer()` 中于离散方向之后叠加逆旋转：

```text
SITL body magnetic field + noise
  -> elliptical calibration inverse / offset
  -> SIM_MAGn_ORIENT 离散逆旋转
  -> SIM_MAGn_ANGL roll/pitch/yaw 小角度逆旋转
  -> board orientation
  -> compass backend
```

参数默认全 0，因而不改变其他 SITL 模型。这个改动解决的是**被控对象/传感器故障注入**，
不是补偿算法本身。同一提交加入的 VRS 模型属于 P01，测试结果反而排除了正常 0.5 m/s
下降时的涡环状态根因，不应混入 P03 成果。

#### 第二步：用方形航线形成可观测数据（`0d6b513474`）

`mag-align` 让六旋翼依次沿 N/E/S/W 四个方向飞行。这样既给 GSF 提供转弯加速度使航向
可观测，又尝试借多航向区分常值安装偏差和随航向变化的磁干扰。离线分析没有使用
`ATT.Yaw` 当磁航向，因为它已经是 EKF 在磁罗盘、IMU、GPS 等信息之间融合后的结果，
会把传感器错误部分吸收掉。

分析器实际执行：

```text
MAG 原始三轴
  + ATT.Roll/Pitch 倾斜补偿
  + 本架次 PARM.COMPASS_DEC 磁偏角
  -> 独立磁航向

XKY0.YC（EKF3 GSF 航向，不融合磁罗盘）
  -> 作为参考航向

稳定直线段上的 wrap(磁航向 - GSF 航向)
  -> 常值均值：安装偏航候选
  -> 一/二次谐波和四象限差：磁干扰候选
```

磁偏角必须从同一日志的参数快照读取。早期曾把 11.6° 写死，而实际为 -5.43°，这会让
全部结果整体平移约 17°。分析只保留航向变化率小于 5°/s、GSF 不确定度 `YCS<=8°`、
时间配对在 0.5 s 内的样本，以减少转弯动态响应差异造成的假偏差。

#### 第三步：发现 ArduPilot 已有连续角补偿，不需要再造机载参数（`fb95f53610`）

第一版判断“固件补不了任意小角度”是错误的。现有 ArduPilot 已提供：

```text
CUST_ROT_ENABLE = 1
CUST_ROT1_ROLL / PITCH / YAW = 估计安装角
COMPASS_ORIENT = 101              # ROTATION_CUSTOM_1
COMPASS_EXTERNAL = 1              # 本项目外置 GPS/罗盘
重新启动并复核
```

数据进入飞控后，`AP_Compass_Backend::rotate_field()` 对外部罗盘调用
`mag.rotate(state.orientation)`；枚举 101 再转入 `AP_CustomRotations` 使用
`CUST_ROT1_*`。内部罗盘走的是板级 `_board_orientation`，所以同样一组设置不会沿完全相同
的路径生效。真实设备必须按每个 compass instance 的 external、priority、orientation
分别确认，不能只看一个参数名。

SITL 注入 +30° 后得到：无补偿辨识 29.93°；设置 -30° 后反而变成 58.03°；设置
+30° 后残余 -3.23°，与零注入时的 GSF 基线偏置相同。因此补偿方向在该 SITL 坐标约定
下得到验证，安装误差相对基线约只剩 -0.07°。真实机安装和传感器驱动的符号仍应通过
已知朝向的地面工装复核，不应凭 SITL 符号直接批量写参数。

#### 第四步：两个“看似独立参考”先后暴露适用边界（`fb95f53610`、`3018c9e8ae`）

一条交叉路线把 GPS 地速写成“机头方向空速 + 恒定风”，并用 4×4 线性最小二乘同时解
安装偏角、风和空速。数学求解没有问题，但“速度方向等于机头方向”的物理前提不适合
多旋翼：位置控制器允许飞机侧飞和迎风 crab。0/8/16° 注入只得到 -0.87/4.12/8.86°，
斜率约 0.55。当前返回键已明确带有
`UNRELIABLE_FOR_MULTIROTOR`，它不能作为 P03 主判据。

另一条主路线使用不融合磁罗盘的 GSF，看起来应当独立；SITL 真值复核却表明：零注入时
独立计算的磁航向相对真值仅 +0.01°，同一架次 GSF 相对真值约 +3.24°。而且 GSF 偏置
随注入 0/8/16/30° 从 +2.60/+1.57/+0.57/-1.64° 单调变化。原因不是 GSF 直接读了
磁罗盘，而是偏航误差改变了闭环飞行姿态和激励，间接改变 GSF 的估计条件。把 YCS 门槛
从 8° 收紧到 1°几乎没有改善。

所以该方法能可靠回答“是否存在大约几十度的固定偏差”，但不能承诺 1° 内的绝对标定。
若需要量产级精度，应采用地面已知机体朝向、双天线 GNSS heading 或其他独立真航向基准。

#### 当前实现中已经确认的假阳性判据

`summarise_mag_align()` 试图用四象限差和一/二次谐波判断“固定安装偏差”还是“磁干扰”。
但纯粹注入 +30° 安装偏差、没有注入磁干扰的现有结果仍输出：

```text
mag_yaw_bias_deg       = 29.93
mag_quadrant_spread    = 19.46
mag_align_verdict      = “随航向变化，属磁干扰，补偿角修不掉”
```

这条 verdict 与已知注入真值矛盾，原因是姿态耦合与 GSF 参考偏置也会形成谐波。当前集中
回归明智地只检查 `mag_yaw_bias_deg` 是否落在 25°—35°，没有采信 verdict；但代码仍把
误导性文本写进结果。建议在建立能分离姿态、软硬铁和参考误差的模型前，把该字段明确标成
实验性/不可用于决策。

#### P03 当前解决程度和正确使用流程

当前能执行的安全流程是：

1. 先确认外置罗盘实例、设备 ID、优先级和粗离散方向正确；
2. 在低磁干扰环境用方形航线或更可靠的地面已知朝向工装采集数据；
3. 离线给出偏角候选及置信度，不在飞行中直接改参数；
4. 人工确认后配置 `CUST_ROT1_*` 和对应 `COMPASS_ORIENT`，重启；
5. 用独立数据复核残余偏角，并保留原参数和一键回退能力；
6. 对多罗盘逐实例检查一致性，再允许进入解锁/飞行基线。

已完成的是“小角度误差仿真 + 固定 Z 轴偏差离线辨识 + 现有参数补偿的 SITL 证明”。尚未
完成的是三轴联合辨识、软硬铁/电流磁干扰分离、多罗盘和 EKF lane 一致性、自动置信度与
回滚，以及机载在线自校正。P03 因此仍是“辨识原型可用、自动对齐未交付”。

### 10.12 P04 电机或桨叶失效：检测、降级分配与着陆的演进

P04 的实现对象目前是 **ESC 有有效 RPM 遥测时的单个电机停转**。SITL 注入
`SIM_ENGINE_FAIL` 后，该路电机的命令输入、转速和推力一起归零。桨叶断裂、脱桨或部分
破损可能表现为电机空载超速、仍有 RPM 但推力下降、强振动和周期力矩，不属于这个检测器
的已覆盖故障。

#### 第一步：先证明原混控会把一个故障放大成两个（`b174199414`）

50 kg、HEXA/DJI_X 模型让 3 号电机停转后，剩余电机总推力仍有很大余量、掉高仅约
0.2 m，但滚转误差达到 44.7°，16.8 s 后因姿态误差坠毁。原有
`thrust_loss_check()` 主要观察“掉高 + 高油门/饱和”，这个场景高度初期几乎守住且剩余
电机不饱和，因此没有触发。

固定前向混控仍假设 3 号电机实际产生指令推力，于是把它不断推到高输出，又将对角 6 号
压到低输出来平衡那份并不存在的力矩，等效为控制器自己削弱了第二台健康电机。首版加入
`MOT_FAIL_IDX` 和 `AP_MotorsMatrix::set_motor_failed()`：从 `motor_enabled` 中移除故障
电机，清除其推力/姿态因子，重新归一化剩余滚转俯仰因子，并将全体偏航因子按
`MOT_FAIL_YAW` 缩放。

早期提交说明把五电机系统描述成“矩阵秩不足”，后续分析进行了更准确的修正：HEXA 少一
台后的 4×5 分配矩阵仍可能具有 4 个独立行，总推力、滚转、俯仰、偏航在代数上有解；但
要求悬停且零偏航时，解会迫使故障电机对面的健康电机恰好为零推力。该配平点位于单向
推力约束边界，某些方向没有调节余量，所以“存在方程解”不等于“在扰动下可控”。

放弃偏航后只保留 `[总推力, roll, pitch]` 三个约束，五台电机留下二维零空间，能把配平
点移回可行域内部。首版人工指定故障电机后，滚转峰值 44.7°→15.4°、俯仰峰值
14.0°→4.3°、水平速度 6.3→0.8 m/s，并能继续留空；代价是约 25°/s 的自旋。

#### 第二步：加入 RPM 停转检测，但默认保持关闭（`d65d58d9b1`）

原 SITL 只有开启振动模型时才计算电机 RPM，默认 ESC 遥测全为 0，无法验证检测器。该
提交把 RPM 状态从振动模型中解耦，为机型 JSON 增加 `max_rpm`，并让转速跟随旋翼出流
状态。

机载检测每个混控周期在 `AP_MotorsMatrix::update_failure_detection()` 中执行：

```text
本路仍 enabled
  AND 上一周期该路 thrust command >= MOT_FAIL_THST
  AND ESC telemetry 有有效 RPM
  AND RPM < MOT_FAIL_RPM 持续 MOT_FAIL_TIME
  -> 唯一一台 suspect：set_motor_failed()
  -> 多台同时 suspect：只告警，不摘除
```

三个参数初值分别为 `MOT_FAIL_RPM=0`（关闭）、`MOT_FAIL_TIME=200 ms`、
`MOT_FAIL_THST=0.15`。低推力不判断，避免下降、spool-down 和上锁时误报；多台同时低转
更像遥测链路或映射错误，直接摘除会主动制造事故。后来 `f2433f587e` 又给多台告警增加
上升沿和 1 s 限频，并在恢复时提示，否则该分支会以 400 Hz 淹没 GCS 消息。

3 号电机实测注入到判定约 0.22 s，结果与人工指定故障编号接近。这证明“低 RPM 的单电机
停转”自动闭环能运行，但由于 `MOT_FAIL_RPM` 默认 0，当前固件默认参数并不会自动启用。

#### 第三步：用带风测试纠正“应该保偏航”的早期判断（`d890978e92`）

无风时保留偏航可把自旋从约 23°/s 降到 2°/s，看起来更好；加入 2 m/s 侧风后，保偏航
使滚转超调达到 68°并坠毁，放弃偏航则滚转稳态约 2.4°并存活。4 m/s 风下对比约为
99.8°和 3.6°。偏航控制与顶风滚转配平争夺的是同一组有限电机余量，因此默认
`MOT_FAIL_YAW` 被改回 0：允许机头旋转，优先守住推力方向和机体姿态。

同一阶段增加逐电机 `motorN_thrust_scale` 故障注入、过渡/稳态分段指标以及
`--land-on-fail`。但要注意：`--land-on-fail` 是测试脚本在注入后主动切 LAND；飞控的
RPM 检测器本身只重构混控并发 STATUSTEXT，**不会自动切换应急着陆模式**。

#### 第四步：从“删列后的前向混控”改为带约束重分配（`e3b63c46b9`）

前向混控先做固定线性组合，越界后再整体缩放或夹紧。少一台电机后，负推力/超上限不再是
偶发情况，事后 clamp 会破坏原本的力矩平衡。`MOT_FAIL_ALLOC=1` 因此启用
`allocate_redistributed()`，只在 `_failed_motor>=0` 时取代正常路径：

```text
demand d = [总推力, roll, pitch]        # yaw 刻意不进入
B       = 剩余电机的 [throttle, roll, pitch] 几何列
u       = B^T (B B^T)^-1 d             # 自由电机最小范数解

若某个 u_i < 0 或 > 1：
  将该电机固定到 0 或 1
  从剩余 demand 中扣除其贡献
  对仍自由的电机重新求解
直到全部在界内，或矩阵退化/残差不可信时回退前向混控
```

最不利 6 号电机、4 m/s 侧风下，首轮报告滚转峰值 16.4°→7.0°、稳态
3.7°→0.2°、漂移 0.8→0.2 m/s。`MOT_FAIL_OPP` 可选择同时关闭对角电机，但默认关闭：
剩余四台并不构成常规四旋翼，特定布局下 yaw 列与 roll 列线性相关，反而丢掉一个独立
控制方向。

#### 第五步：利用零空间降低寄生偏航（`2e28b95347`）

放弃偏航需求后，满足总推力/滚转/俯仰的五电机解不唯一。普通最小范数只最小化电机推力
平方和，不关心剩余旋翼真实产生的寄生偏航力矩。`MOT_FAIL_YSUP` 在同一零空间中偏置
解，使目标近似成为：

```text
minimise ||u||^2 + k * (yaw_geometry^T u)^2
subject to B_rpt * u = demand_rpt, 0 <= u <= 1
```

实现必须在清零实时 `_yaw_factor[]` 前保存物理几何 `_yaw_geom[]`；曾经直接使用已清零
因子，导致参数看似生效但三档测试完全不变。修正后 6 号停转、4 m/s 风时，k=0/0.5/
0.95 的平均偏航率约为 22.1/19.3/17.0°/s，滚转峰值基本不变。它只能减慢自旋，不能
恢复航向控制。

#### 第六步：一次“姿态很好”的假成功掩盖了持续掉高（`0cc63606fc`）

分配器把传入的 throttle 当作所有电机总和，但前向混控语义是每台电机都获得一份基准
throttle。少一台后求解器错误地让五台电机合计等于一份油门，每台仅得到约 1/5。飞机从
15 m 持续下降，直到高度环把油门推满；满油门的 1/5 又恰好略高于五电机悬停所需值，
于是它能在更低处稳定，姿态、漂移和“仍解锁”指标都很好看。

修复是将油门方程的 demand 乘以当前参与分配的电机数。更重要的是回归加入掉高 `<2 m`
且缺失高度直接失败。修复后 6 号停转、4 m/s 风的现有结果为：检测约 0.23 s、掉高
约 0.04 m、最大水平偏移约 0.116 m、滚转峰值 6.84°、滚转稳态约 2.0°，持续留空。

这段历史说明“姿态稳定”不能替代“状态稳定”：P04 至少要同时检查高度、位置、姿态、
角速度、剩余推力裕度和最终是否安全着陆。

#### 第七步：继续修复求解器本身的两类危险假成功（`f4f8550de2`、`9c7f099288`）

`f4f8550de2` 发现首轮矩阵求逆失败时，初始化为全零的输出仍被当成 true 返回，调用方会
把六路推力清零；病态矩阵还可能产生巨大有限数或 NaN，随后 clamp 成看似合法的 0/1 或
0.5。修复加入：只有验证过完整解才返回 true、非有限数拒绝、将解代回 `B*u` 做 1%
相对残差检查，失败则保留前向混控。

`9c7f099288` 又发现 `have_solution` 在“本轮发生夹紧、仍需下一轮重解”时就被置 true。
若下一轮因自由电机不足而退化，函数会提交“夹紧电机用边界值、自由电机仍用上一轮按未
夹紧假设算出的值”的不一致组合。最终改为仅在一整轮无任何 clamp 后才承认解成立。

这两个修正都晚于最初漂亮的 P04 数据，意味着早期“通过”不足以证明分配器在饱和边界
安全；必须用修正后的提交重新覆盖不可行 demand、病态几何和多电机限幅。

#### 第八步：把实际分配结果反馈给 PID，并增加 `MALC` 日志（`e1ce30b6dd`）

原 `limit.roll/pitch/yaw/throttle_*` 由前向混控设置，随后重分配器却整体覆盖了各电机
输出。速率 PID 的 anti-windup 因此一直依据一套没有真正执行的混控结果。新版本用最终
推力回算 achieved，对未满足的轴重置 limit 标志：roll/pitch 按缺额，油门区分上/下限；
yaw 没有进入求解，始终报告受限，阻止偏航积分继续累积并挤占姿态余量。

`MALC` 记录 demand 和 achieved，使日志能区分“控制器要求错误”与“分配器交付不足”。
不过当前 `AYaw` 用的是被 `MOT_FAIL_YAW=0` 清零后的 `_yaw_factor[]`，所以它记录的是
**分配器所声明的偏航通道输出 0**，不是剩余旋翼按 `_yaw_geom[]` 实际产生的寄生偏航
力矩。`MOT_FAIL_YSUP` 明明依赖 `_yaw_geom`，而 MALC 不记录这项，字段说明中的
“Yaw moment achieved”会误导故障后物理力矩分析。建议同时记录几何寄生 yaw，或给现有
字段改成明确的“受控 yaw 通道 achieved”。

#### 后续合入的两项参数安全修正

`45000cab3a` 之后又有两个 P04 修正，并已通过 `5d1a8b7dbf` 合入后续分支：

1. `610f3f639e`：指出默认 `MOT_FAIL_ALLOC=1` 时求解器固定
   `include_yaw=false`，会覆盖前向混控，因此 `MOT_FAIL_YAW` 无论设多少都静默无效。
   远端没有让危险的偏航追踪重新进入分配，而是在预解锁时拒绝
   `FAIL_ALLOC>0 && FAIL_YAW!=0`，并明确只有 `MOT_FAIL_YSUP` 会影响约束分配器；
2. `e79a134719`：`MOT_FAIL_IDX` 是持久参数，而 RPM 检测器实际直接调用
   `set_motor_failed()`、从不写它。台架测试若忘记清零，下一次会在解锁后第一拍才静默
   摘掉一台电机。远端因此在地面发现 `FAIL_IDX!=0` 时拒绝解锁。

`4170db8d3b` 的提交记录表明包含这两项的 EFT_CAAC 编译通过；但预解锁拒绝路径仍应增加
参数组合单元测试和台架检查，不能只依赖正常参数下的飞行回归。

#### P04 当前能力边界

已有证据支持：目标 HEXA/DJI_X 模型、单台电机完全停转、有可靠 ESC RPM、已启用阈值、
指定失效位置与测试风场下，约 0.22 s 检测后可重分配并保住姿态/高度；脚本主动切 LAND
时，4/8 m/s 风下从约 15 m 完成着陆，最大水平偏移约 0.21/0.23 m。

仍不能宣称已经解决“电机或桨叶失效”的全部问题：

1. RPM 检测默认关闭，阈值是固定绝对值，未按命令、电压、负载和每台电机基线做残差；
2. 不覆盖部分失推、桨叶断裂/脱桨导致的超速与振动、ESC 遥测错误或失联；
3. 检测后不会自动进入受控应急着陆，当前 LAND 成功由测试脚本触发；
4. 只允许每次上电不可逆摘除一台，误报后没有空中回滚；
5. 缺少硬件在环、系留和真实教练机六个位置、载荷/电量/风向的完整矩阵；
6. 失效后持续自旋约 15—20°/s，视觉、GNSS 航向、喷洒、避障和着陆方向的上层功能都
   需要明确降级；
7. 饱和时若约束解失败会回退前向混控，尚无按轴优先级求“最接近可实现 wrench”的完整
   降级策略。

最准确的项目状态是：**“单电机完全停转”的 SITL 检测与姿态/高度保持原型已闭合，自动
应急着陆和桨叶类故障尚未闭合，实机功能默认不应开启。**

### 10.13 P05 电子围栏：从“越界后动作”到姿态模式主动刹停的演进

P05 首先要分清三层职责，否则很容易把一次“最后停住”误写成“没有出围栏”：

1. **任务/路径合法性**：起飞前或新路径生成时，检查航点、航段、转弯圆弧和避障路径是否
   全部位于围栏及安全余量内；
2. **越界前指令限制**：飞机仍在围栏内时，根据剩余距离、速度、风和可用减速度，修改速度
   或姿态指令，使飞机停在边界以内；
3. **越界后处置**：`AC_Fence` 检出 breach 后，由 `FENCE_ACTION` 执行 Brake、Loiter、RTL
   或 Land 等失效保护。

开发前的 AUTO 用例最大半径约 45.8 m，而围栏半径为 40 m。它证明的是越界约 5.8 m 后
Brake 最终把飞机停住，属于第三层，不能作为“稳定飞行而不出围栏”的验收证据。P05 这组
提交主要补的是第二层中的**手动姿态输入模式**。

#### 第一步：先修测试协议，否则围栏“成功上传”本身就是假象（`799ed74fda`—`d8c2c4708b`）

首批提交没有动飞控算法，而是连续修复测试脚手架：

- 用 MAVLink `MAV_MISSION_TYPE_FENCE` 上传多边形围栏，并按 `mission_type` 过滤
  `MISSION_ACK`；此前清空任务的 ACK 可能被围栏上传误收，围栏 ACK 也可能被普通任务上传
  消费，脚本会在没有上传正确对象时继续测试；
- 修复命令行 `--set` 被场景内部硬编码参数静默覆盖的问题，并让结果保存实际受测模式；
  此前即使要求测其他模式，脚本仍可能切回 LOITER；
- 增加多边形旋转、任意顶点和进场航向，以覆盖顶点、边心和凹多边形；
- 明确圆形围栏的径向余量不适用于多边形，随后把多边形指标改成距最近边的带符号法向
  距离（`5fd4e296a7`）。脚本与 EFT 日志的独立计算差约 0.01 m。

这些提交说明，场景生成、协议 ACK 和几何指标也是证据链的一部分。若它们不可靠，算法
前后的漂亮数字没有可比性。

#### 第二步：补上姿态模式绕过速度围栏的结构缺口（`f68454c187`）

LOITER 等位置/速度控制模式的飞手输入最终会形成目标速度，已有
`AC_Avoid::adjust_velocity_fence()` 可以在围栏附近收紧速度。ALT_HOLD、POSHOLD 和
STABILIZE 的横向杆量直接形成 roll/pitch 目标，原调用链只经过基于接近传感器的
`adjust_roll_pitch_rad()`，没有进入围栏速度路径；因此在 breach 前飞手仍可持续给出向外
倾角。

首版增加 `AC_Avoid::adjust_lean_for_fence_rad()`，调用链变为：

```text
飞手 roll/pitch 目标
  -> 按当前 yaw 将倾角换成 NE 水平加速度
  -> 以短前瞻得到“若继续执行杆量将达到的目标速度”
  -> 复用 adjust_velocity_fence() 的圆形/多边形/排除区/beacon 几何
  -> 将允许速度反算成水平加速度
  -> 再变回机体系 roll/pitch，并按最大倾角做向量限幅
  -> 姿态控制器
```

这样没有复制一套围栏几何，并将 ALT_HOLD、POSHOLD、STABILIZE 的限幅放在真正送往姿态
控制器之前。60 m 六边形、5 m 余量的首轮结果中，三种模式原先最远约
866—903 m，接入后停在约 55.1—55.6 m；LOITER 路径保持原行为。

#### 第三步：首版“不得超过飞手杆量”会让松杆后的飞机完全不刹车（`55cceb32b3`）

首版有一道安全兜底：算法修正后的倾角幅值不能大于飞手输入，避免围栏估计错误时飞机
自行做大动作。但姿态模式中松杆只表示零倾角，不等于位置制动；已有水平速度会继续滑行。
所以飞手在边界前松杆时，所需反向刹车被幅值兜底压回零，SITL 曾滑出约 856 m。

修正后的判据不再比较“是不是大于飞手”，而是比较**方向**：仅当新增加速度与当前速度
点积为负、即确实在制动时，允许倾角超过飞手幅值；后来的退避速度也作为另一种允许情况。
它恢复了松杆刹车，同时仍禁止围栏算法无缘无故生成横向机动。

#### 第四步：有风时只限速度会形成非零稳态爬行（`a54a00ff91`）

`adjust_velocity_fence()` 除了返回限后的速度，还单独返回把飞机推出余量带所需的
`backup_vel`。姿态层首版忽略了它，只剩近似 `-v/T` 的速度阻尼。恒定风扰动与阻尼平衡
后会留下一个向外的稳态速度，飞机虽然很慢，仍会一步步穿过余量；一旦到了围栏外，预防
限制不再是可靠的恢复控制，满杆甚至会继续把飞机带走。

修正将 `backup_vel` 合入目标，并按 `g*tan(veh_angle_max)` 所代表的机体可实现加速度
限幅，而不是沿用位置控制模式的固定 `AVOID_BACKUP_SPD`。这关闭了“无风能停、有风慢慢
爬出”的首个缺口，但后来现场高速顺风测试证明，光有退避项仍不够。

#### 第五步：后续审查先证明此前多组姿态模式结果飞在错误高度（`f2433f587e`—`42bfbe41ca`）

S7 的 `f2433f587e` 又发现 DRIFT 和 FLOWHOLD 也属于没有自然经过速度围栏的路径：

- DRIFT 的飞手 roll/pitch 会在松杆后被内部 auto-brake 覆盖，因此围栏必须插在最终倾角
  形成以后；
- FLOWHOLD 同样在最终 `bf_angles_rad` 上调用硬围栏限制，但当时没有可用光流 SITL 证据，
  只能确认静态调用链，不能宣称动态通过。

同时，`cd2b5809a6` 为每个用例生成唯一 variant，避免同名日志覆盖；`90108bc081` 让收尾
超时不再作废已经取得的有效测量，并改用 GUIDED 回到场中心，避免在风中用机体系反向杆量
回飞。

更关键的是 `42bfbe41ca`：姿态模式测试原先用固定油门 PWM，飞机分别爬到约 95、471、
甚至 1927 m。高度越高、垂向状态越异常，姿态可用推力余量和场景真实性越差。加入围绕
15 m 的 P-D 定高环后，才建立可比较的水平围栏试验。因此它之前关于各模式、尤其风速上限
的数字必须视为已失效的探索证据，不能直接写入验收结论。

#### 第六步：现场六次越界定位到制动律缺少剖面前馈（`eb8de1cdfd`）

2026-08-31 现场日志使用 `55cceb32b3` 固件，共出现 6 次 breach，其中 5 次在顺风侧，
最深越界 18.57 m。逐拍复原显示，飞机从约 22 m 外向边界接近时，实际速度持续比允许
速度高约 0.7—1.6 m/s，但代码大部分时间只下发 5.6—7.3° 刹车倾角；机体限制 15°，
即约 2.63 m/s²，直到越界前约 0.5 s 才接近满刹车。问题不是“机体刹不住”，而是控制律
没有及时要求它刹。

旧律本质为：

```text
a_cmd = (v_allow - v_out) / T
```

停止剖面 `v_allow(s)=sqrt(2*a_profile*s)` 上，飞机要一直留在这条剖面上，本来就需要
`a_profile` 的持续减速度；旧式在 `v_out == v_allow` 时却恰好给零，只会在飞机先超速后
才生成制动，形成永久的剖面跟踪误差。新律从剩余距离反解所需减速度：

```text
a_req = a_profile * (v_out / v_allow)^2
a_req = min(a_req, a_airframe)
```

在剖面上直接给 `a_profile`，超速时按平方增加，余量线附近 `v_allow` 接近零时使用机体
最大能力；飞机已经向内运动时不给无意义的反向制动。实现只替换围栏法向的外推分量，保留
飞手沿围栏切向运动的权限。按现场近似工况——44×52 m 多边形、1 m 余量、15°倾角限制、
4.9 m/s、038°风——四个方向均停在边界内约 0.61—0.69 m，未 breach。

#### 第七步：让剖面采用机体能力，并补真正的高速冲刺场景（`b34dc4c113`、`45000cab3a`）

`b34dc4c113` 当时的解释是：速度层历史常量 `AC_AVOID_ACCEL_CMSS_MAX=1.0 m/s²` 对不同
机型不代表相同刹车能力；从 7 m/s 停车需约 25.5 m，超过现场田块约 22—26 m 的半宽，
所以剖面放不进场地。基于该解释，它将姿态围栏专用剖面改为
`g*tan(veh_angle_max)`，目标机 15°时约 2.63 m/s²，对应 7 m/s 理论制动距离约 9.3 m。
当前 `AC_AVOID_FENCE_PROFILE_FRAC=1.0`，即剖面直接使用全部名义能力。这个“为何有效”的
解释随后在第八步被更正，但代码取值保留。

此前“持续满杆 70 s”更像稳态推栏，不能保证飞机真的先达到指定高速。
`45000cab3a` 因此增加 `fence-sprint`：在约 24 m 半宽内分别达到 3/5/7 m/s 后冲向最近边，
并通过实际运动方向辨识杆量符号，修复了 pitch=2000 被误认为前进、纯 P 速度环达不到目标、
冻结点过早以及射线交点不是最近边等脚手架问题。该提交建立了正确的高速验收入口，但提交
说明没有给出一套完整、可复核的 3/5/7 m/s 最终结果，不能把“场景已加入”等同于“全部
速度已通过”。

#### 第八步：纠正“剖面决定刹车距离”和“3/5/7 m/s 全通过”的两次过早结论（`d8296fdd18`—`ead4a24364`）

`d8296fdd18` 指出，上述“1 m/s² 剖面需要 25.5 m、2.63 m/s² 只需 9.3 m，所以后者才
刹得住”的解释已经被 `eb8de1cdfd` 的新命令律改变：真正需要制动时，`a_req` 会按速度比
平方增加并最终饱和到机体能力，两种 profile 都可能用同样的最大刹车。因此 profile 主要
决定的是**多早介入、靠近围栏时还允许飞多快**，而不是最终满刹车能力。

在 15°、半宽 24 m、1 m 余量和 5 m/s 顺风下，降额剖面约把巡航钳在 3.0—4.5 m/s，
而 full profile 能到约 5.0—7.1 m/s；两者都能停在栏内约 1.0—1.3 m。于是保留
`PROFILE_FRAC=1` 的正确理由是避免围栏限制覆盖大部分地头、过早损失作业速度，而不是
声称低比例一定刹不住。该提交又加入无风和现场工况两条 sprint 回归，同时检查“不越界”
和“巡航速度不能被错误压低”。

随后 `9a7776fe79` 给普通 `fence` 增加可选速度档，并报告现场几何下 3/5/7 m/s 三档均停
在约 0.61—0.69 m、因此“速度无关”。`ead4a24364` 立刻撤回了这项结论：

1. `9a7776fe79` 因 `pull --rebase --autostash` 冲突，把两处 `<<<<<<<`/`>>>>>>>` 标记直接
   提交，脚本语法错误；之前的 `ast.parse` 在 pull 前执行，不能证明提交后的文件可运行；
2. 用来下结论的 `speed_at_closest_m_s` 是最接近围栏、已经刹停时的速度，本来就趋近零，
   不是进场速度；
3. 从日志重算的 `approach_speed_p95_m_s` 实际为约 2.76/4.42/4.43 m/s，后两档根本没有
   分别达到 5/7 m/s，所以“三档速度无关”和“7 m/s 已关闭”都没有证据。

紧急修复保留普通 fence 的 `--fence-speeds` 与 sprint 的 `--sprint-speeds/--sprint-back`，
并输出真正的进场速度指标。这里最重要的不是一次语法修复，而是结论纪律：测试目标速度、
实际达到速度、最接近边界时速度是三个不同量，不能混用。

#### 当前最终调用链与控制量含义

截至 `ead4a24364`，ALT_HOLD、POSHOLD、STABILIZE、DRIFT 和 FLOWHOLD 最终都会在
把横向倾角交给姿态控制器前调用 `adjust_lean_for_fence_rad()`；LOITER 已走速度限制路径。
核心过程是：

```text
实际 NE 速度 + 飞手倾角
  -> 一秒前瞻速度
  -> 全部已支持围栏几何给出的允许速度、退避速度和外法向
  -> 法向实际速度 v_out / 法向允许速度 v_allow
  -> 平方制动律计算 a_req，并受名义倾角能力限制
  -> 保留切向飞手加速度，只把外向分量替换成向内制动
  -> 转回 roll/pitch，做总倾角限制
  -> 只有“制动”或“退出余量带”可超过飞手原杆量
```

这条链路解决的是“有有效位置/速度估计时，姿态输入模式的水平围栏越界前主动限制”，
不是一个接管所有模式、所有路径和所有故障的统一安全控制器。

#### P05 当前能力边界和建议

1. `adjust_lean_for_fence_rad()` 取不到 AHRS NED 速度时直接返回、保留原杆量。位置或速度
   估计失效时必须由 EKF failsafe 和 `FENCE_ACTION` 接管，不能把预防限幅当唯一屏障；
2. 各姿态模式传入 `attitude_control->lean_angle_max_rad()` 作为“机体本周期可实现能力”，
   但 ALT_HOLD/POSHOLD 的飞手目标还会受随垂向推力裕度变化的
   `get_althold_lean_angle_max_rad()` 限制。重载、爬升或电机降级时，围栏可能按比实际可用
   更大的水平减速度设计停车剖面；应改为使用当前真正可用的动态倾角/推力裕度；
3. `PROFILE_FRAC=1` 让名义剖面占满全部倾角能力，模型误差、GNSS 误差、阵风和执行器时延
   的制动储备很薄。比例需要通过实机辨识和最坏工况选取，不能由一架 SITL 模型定值；
4. 1 m `FENCE_MARGIN` 即使 SITL 停在栏内约 1 m，也几乎不给真实 GNSS 与场地测绘误差
   留空间；而最新所谓 7 m/s 用例实际只达到约 4.43 m/s。任务速度上限应满足“制动距离 +
   状态估计误差 + 风/时延储备 ≤ 可用距离”，并以实际进场速度验收；
5. FLOWHOLD 尚无光流动态验证，凹多边形、排除区、顶点切换、竖直围栏、多 EKF lane 和
   定位跳变也缺少完整矩阵；
6. AUTO、GUIDED 圆弧和 OA 不能只依赖越界后的 Brake。`d77cb9757b` 已对协调转弯的理想
   圆弧做围栏采样，但任务航段、三维平滑过渡和动态避障路径还没有统一的全路径合法性证明；
7. 现场六次 breach 发生在关键制动律修正之前。新律虽复现了现场近似条件，仍必须在教练机
   上用同步日志、参数、围栏文件、风况和视频重新做由低速到高速的渐进验证。

`d8296fdd18` 的 profile A/B 与两条 sprint 回归已经提交；但 `ead4a24364` 证明普通 fence
的后两档实际速度重合，7 m/s 高速边界仍未取得有效证据。下一轮必须同时报告设定速度、
`approach_speed_p95_m_s`、开始限幅速度、最大制动和最小余量，并在提交后重新做语法检查。

最准确的项目状态是：**姿态输入模式的水平围栏主动限制已经从结构缺口演进为按制动距离
控制的原型，并用现场失败反向修正过核心公式；但动态推力裕度、全模式/全路径覆盖、真实
定位误差与修正后实机复飞仍未闭环，不能承诺任何情况下绝不越界。**

### 10.14 P01 着陆：当前分支完成的是复现与排因，还没有交付机载解决算法

从算法开发起点的父提交 `8bf9f2e035` 到远端 `origin/dev-algo`，
`ArduCopter/mode_land.cpp` 和 `ArduCopter/land_detector.cpp` 没有 P01 专项差异。因此不能
说这个分支已经通过修改着陆控制器解决了“末段不拉平、刚性接地、落地识别慢和触地后
电机对抗”。P01 的真实演进是：**先把现场因果链变成可测试场景，逐个排除候选根因，再
暴露当前 Lua 缓降策略在无测距仪条件下的结构风险。**

#### 现场证据与真正需要解释的三个子问题

现有真机资料不是一个单指标问题：触地下降率约 0.33—0.67 m/s，冲击约
1.31—3.04 g；部分落地在接触后约 1.02—1.47 s 才完成落地识别；触地后六路电机输出
极差曾达到约 271—347 PWM。三者分别对应：

1. **接地前能量**：末段下降速度是否随接近地面连续减小；
2. **触地判定**：冲击后各判据多久才连续满足，何时置 `land_complete`；
3. **触地后退出**：垂向与姿态控制器如何卸载，电机是否继续顶住不平地面。

当前教练机没有测距仪，起落架有效缓冲行程又只有约 5 mm。因此软件可以降低入射动能，
但不能把刚性脚架变软；而“按真实离地高度连续拉平”也不能凭空获得，只能依赖相对 Home/
terrain 高度及运动状态，或把增装测距仪作为另一个产品决策。

#### 第一步：建立六旋翼 AUTO 着陆闭环与直观视频入口（`19b4e4c3c3`）

`reproduce.py landing` 上传并执行：

```text
Home -> AUTO TAKEOFF 8 m -> 两个 25 m 航点 -> NAV_LAND -> 自动上锁
```

监视器从 `SIM Hit ground at ...` 记录真实接地速度，从 armed 状态变化记录上锁时刻，并在
触地后 1.5 s 内统计前六路 PWM 极差；`render_video.py landing` 则把问题物理模型和基线
并排渲染。它第一次把“肉眼觉得砸”拆成可回归的触地速度、触地到上锁时间和电机差值。

同一提交的首版近地模型是人为构造的瞬时项：在指定高度以下把
`ground_effect_gain + ground_effect_vspeed_gain*v_down` 乘到总推力上，并在极低高度人为
线性溃散。它能构造“托举—控制器收油—接地前托举消失”的现象，但模型没有诱导流状态，
参数也不是从实机辨识得到，所以只能作为假设生成器，不能用来证明真实机理。

#### 第二步：用物理结构替换人为溃散模型（`d46eb5c65e`）

后续主动放弃了容易“调参数调出砸地”的首版公式，改成：

```text
静态地效：T_IGE/T_OGE = 1 / (1 - (R/(4z))^2)
           并用 ground_effect_kmax 限制近地发散
下降折减：1 / (1 + (v_down/vref)^2)          # vref=0 时关闭
动态地效：对目标增益做时间常数 ground_effect_tau 的一阶滞后
```

`Frame` 保存跨仿真步的 `ground_effect_state`，并从 `Aircraft` 取得实际仿真步长。模型按
39 英寸桨半径约 0.5 m、0.25 m 高度处托举量约 8.5% 的量级设置
`ground_effect_gain=0.26`，但提交明确说明这不是辨识结果。

新模型产生了约 0.31 m 开始托举、垂向加速度环 P 项转负和油门下调的“前半段”；然而
0.5 m/s 指令下，触地速度只有约 0.427—0.439 m/s，比指令还慢。也就是说它没有复现
真机最关键的“最后突然加速下坠”。这是一次重要的负结果：物理结构正确性优先于把曲线
硬调得像现场。

#### 第三步：补 VRS 后排除正常着陆速度下的涡环根因（`0d6b513474`）

原 `SIM_Motor` 将桨盘轴向来流钳在非负区间，下降段气动等于被抹掉。新模型按
`eta=v_down/v_hover_induced` 构造钟形推力损失，峰值约在 `eta=1.1`，由
`vrs_gain/peak/width` 控制，默认增益 0 不改变其他机型。

但在本机约 0.5 m/s 的正常着陆中，`eta` 只有约 0.08。实测：

| `vrs_gain` | 0 | 0.25 | 0.45 |
| --- | ---: | ---: | ---: |
| 触地速度 | 0.4297 m/s | 0.4275 m/s | 0.4274 m/s |

差异可以忽略，说明 VRS 不是这类正常下降率砸地的解释。按当前占位机型，下降率约到
3 m/s 以上才进入需要关注的区间；除非现场高速日志证明有这种下降率，否则不应继续靠调
VRS 参数解释 P01。

#### 第四步：地效时间常数 A/B 仍不能生成加速下坠

现有结果中 `ground_effect_tau=0.05/0.15/0.30/0.50 s` 的触地速度约为
0.437/0.428/0.431/0.443 m/s，触地到上锁均约 1.8 s。时间常数会改变最后几厘米的托举
历史，但在当前静态结构下仍没有把 0.5 m/s 着陆变成现场观察到的超速接地。因此下一步
不能继续在这一个参数上寻优；需要触地前高速率 PIDA/CTUN/IMU 和真实机体参数，辨识地效
建立/消散与控制器收油之间的动态关系。

#### 第五步：复现无测距仪 Lua 缓降脚本提前“放开限速”的危险（测试脚手架后续演进）

现场 `land_speed_by_relalt.lua` 的思路是：相对 Home 高度低于 `LNDS_ALT_M` 时，把
`LAND_SPEED` 等参数压到缓降值；低于 `LNDS_REL_M=0.15 m` 后锁存并恢复基准速度。问题是
该高度并非真实离地高度。实机日志中，物理触地时 EKF 相对 Home 高度可为
-0.74—-1.13 m，所以它可能在真实地面上方约 1 m 就穿过 0.15 m 门限并恢复较快下降。

`run_landing(release_alt_m, release_speed_cms=200)` 用 SITL 真离地高度直接注入“提前恢复
到 2 m/s”，用来复现后果而不是假装 SITL 有同样高度漂移。脚手架首版依赖
`EXTENDED_SYS_STATE` 判断已起飞，事件可能根本未触发；改为先确认高度超过 3 m 后，
A/B 才真正有效：

| 提前释放的真实离地高度 | 触地速度 | 触地到上锁 |
| --- | ---: | ---: |
| 不释放，保持正常 LAND | 约 0.428 m/s | 1.80 s |
| 0.5 m 恢复 2 m/s | 0.964 m/s | 1.86 s |
| 1.0 m 恢复 2 m/s | 1.397 m/s | 1.88 s |

这证明了机制的危险性和量级，但尚不能证明现场脚本当时确实走了这条分支，因为原日志中
`LNDS_DBG=0`、没有 `LNDX` 事件，且部分时序证据仍对不上。下次现场必须开启脚本调试日志，
同时保存运行期实际参数值；Lua `param:set` 只改内存，不能仅凭起飞前/日志中的参数快照
推断着陆时实际使用值。

#### 第六步：落地识别“触地冲击把计数清零”的猜测已被 A/B 否定

曾探索过在 `land_detector.cpp` 记忆接触冲击、缩短去抖的方案，但 A/B 中触地到上锁仍为
1.82 s，因此代码被撤回，没有留在 `dev-algo` 当前差异中。`LDET` 解码显示：限制计数开始
的主要条件是 `MOTOR_AT_LOWER_LIMIT`，不是 `ACCEL_STATIONARY`；触地后约 0.12 s 去抖便
正常开始。总延时中约 1.1 s 是连续判据计时，其余来自后续 spool/上锁链，而不是简单的
“冲击每次把判据清零”。

当前标准执行链仍是：

```text
ModeLand::run/gps_run
  -> Mode::land_run_vertical_control()
     -> 用 get_alt_above_ground_m() 和 LAND_ALT_LOW 生成下降速度
     -> LAND_SPEED / LAND_SPEED_HIGH 约束
     -> AC_PosControl::land_at_climb_rate_ms()
     -> AC_PosControl::update_U_controller()

Copter::update_land_detector() @ MAIN_LOOP_RATE
  -> motor lower limit + throttle mix min
  -> 小姿态目标/小姿态误差
  -> 加速度平稳 + |垂速|<门限
  -> 测距仪条件/WoW 条件
  -> 连续计数 -> land_complete_maybe -> land_complete
  -> ModeLand 等待 GROUND_IDLE 后 disarm
```

没有健康测距仪时，`get_alt_above_ground_m()` 会尝试 terrain 高度，最后退回相对 Home 的
“平地假设”；land detector 的 rangefinder 条件则因传感器无效而直接放行。这既解释了
为何末段拉平缺少可靠地面基准，也说明不能单纯缩短整个 land detector 时间常数——在空中
近零速度、低油门或扰动条件下会增加误判落地并停桨的风险。

#### 第七步：后续地效力计算次序修正（`abd7da79ec`）

`abd7da79ec` 发现地效原先在扣除机体阻力后再乘：

```text
(rotor_thrust - body_drag) * (1 + ground_effect)
```

这会错误地把机体阻力也按地效放大。修正为先放大纯旋翼推力，再扣机体阻力。错误在离地
约 0.25 m 以下才明显；按本场景 0.43 m/s 接地，其量级约占重量 0.06%，修正前后仍为
0.43 m/s 和 1.80 s，因此不推翻既有结论。它只影响 SITL，不改变机载固件。

#### P01 当前能力边界和下一步

当前分支已经完成：统一 AUTO 着陆场景、视频渲染入口、触地/上锁/PWM 指标、地效动态
模型、下降段 VRS 模型、候选根因排除，以及 Lua 高度门限提前释放的危险复现。尚未完成：

1. 没有实现并验证“随接近地面连续减速”的新机载包线；
2. 没有对 `land_detector` 提交更快且证明不增加空中误停桨风险的新判据；
3. 刚性 SITL 地面触地后六电机极差只有约 18—28 PWM，远小于真机约 271—347 PWM，
   所以触地后地面对抗没有复现；
4. 50 kg、惯量、2 m 轴距、4.71 m² 总盘面积以及地效参数仍是占位/量级参数；
5. `LAND_SPEED` 从 0.5 降到 0.3/0.2 m/s 的历史 A/B 只证明降低动能的直接收益，同时会
   延长着陆和判定时间；现场 Lua 会动态覆盖参数，必须从实际运行链验证；
6. 当前没有修正后机载算法可供实机 A/B，不能将“回归触地 0.43 m/s”写成问题已解决。

最准确的状态是：**P01 的复现、测量与排因取得了实质进展，并找到相对 Home 高度提前
释放缓降的高风险路径；但最终分支仍使用原 ArduPilot 着陆控制/检测代码，末段拉平、快速
可靠触地识别和触地后平滑卸载三项均未交付。**

### 10.15 P08 常态偏航配平：解决七项时新发现的问题及其唯一代码提交

P08 不是最初七项之一。它来自 `5e5dd769eb` 对“IMU 失真或动力系统不一致”替代根因的
检查，符合项目约定的“解决过程中发现新问题可以新增编号”，不应覆盖或重命名 P01—P07。

三份实机日志 00000219/220/231 都显示：同旋向三台和反旋向三台电机稳定分成两组，RPM
离散约 41.7%—47.1%，电流离散约 106%—115%，RCOU 指令不对称约 8.1%—12.6%；同期
`RATE.YOut` 均值分别约 -0.142/-0.072/-0.111，航向误差却只有约 0.19°—0.35°。最直接
的解释不是“飞控没有保持航向”，而是飞控正通过持续占用约 7%—14% 偏航控制量来抵消
机架常态偏航力矩，因而主动把两组反向旋翼推到不同工作点。

`2c765bba39` 只增加一个 SITL 被控对象参数 `yaw_torque_arm_m`：

```text
yaw_disturbance_torque = yaw_torque_arm_m * total_rotor_thrust
```

电机座切向倾角、CW/CCW 桨不匹配和机架扭曲虽是不同硬件原因，宏观上都可表现为随总
推力变化的偏航矩。用等效力臂统一注入后，0/0.005/0.010/0.020/0.040 m 扫描得到：

| 等效力臂 | RCOU 不对称 | RPM 离散 | `RATE.YOut` 均值 |
| ---: | ---: | ---: | ---: |
| 0 | 4.4% | 12.2% | -0.026 |
| 0.005 m | 6.9% | 22.7% | -0.064 |
| 0.010 m | 9.3% | 32.8% | -0.105 |
| 0.020 m | 14.6% | 54.4% | -0.197 |
| 0.040 m | 25.3% | 116.5% | -0.616 |

实机三组特征大致落在 0.010—0.015 m 等效力臂；若暂按占位的 1 m 臂半径换算，相当于
约 0.57°—0.86° 切向倾角。这只是量级映射，不是把根因锁定成电机座倾角：臂长、偏航
阻力系数、推力曲线和 ESC 标定都未用真机台架数据标定，正反桨气动差也可能形成同一特征。

这项提交完全位于 `SIM_Frame`，没有增加机载补偿算法。这个选择是合理的：现有偏航 PID
已经把航向误差压得很小，再加软件偏置只会把持续配平从一个地方搬到另一个地方，不能消除
两组电机的能耗和寿命不均。正确处理顺序是：

1. 地面核对 1—6 号电机映射、旋向、CW/CCW 桨型号与安装方向；
2. 用分辨率不差于 0.1° 的工装逐台测切向安装角，照片或手机量角精度不够；
3. 台架建立每路同命令下 PWM→RPM→推力→电流曲线，区分“飞控主动给不同命令”和“同命令
   动力链性能不同”；
4. 修复物理原因后重复同一悬停/定速任务，看 `YOut`、RPM/电流和 RCOU 三组证据是否共同
   收敛；
5. 重新核算 P04 单电机失效后的推力和偏航裕度，因为原机已经预先消耗了一部分权限。

当前状态是：**实机异常特征和一个可解释其量级的等效物理模型已经建立；具体硬件根因未
经现场测量确认，分支也没有、原则上不应优先增加掩盖机械问题的机载软件补偿。**

### 10.16 S7/S8 横向修正：为什么后半段提交不能按单个问题孤立阅读

S7/S8 的价值主要在于用审查和集中回归推翻前一阶段过早的结论。它们不是“又写了两轮新
算法”，而是把每项原型从“能跑一次”推进到“结果来源、模式、参数和失败原因可追溯”。
